## Principle

**System Status Visibility**: Keep users informed about what's happening through clear, immediate feedback. Never leave users wondering if their action worked.

## The Problem

Financial systems involve high-stakes actions where users need confidence that operations completed successfully. Traditional enterprise systems often fail by:

- **Silent failures**: Actions fail with no indication
- **Vague messages**: "Error occurred" with no context
- **Delayed feedback**: Wait 5-10 seconds to see if it worked
- **Unclear status**: Is it processing? Did it complete? Did it fail?
- **No confirmation**: Action completes silently, users uncertain
- **Hidden errors**: Problems buried in logs, not shown to user

This creates user anxiety and distrust:
- **"Did that work?"** - Users click repeatedly
- **"Should I try again?"** - Risk of duplicate transactions
- **"What went wrong?"** - No actionable information
- **"Can I trust this?"** - Confidence eroded by opacity

Financial platforms especially need to communicate clearly because mistakes have real monetary consequences.

## Stripe's Implementation

Stripe's documentation presents the Dashboard as an operational surface for finding
transactions, inspecting status, managing payments, monitoring an integration, and exporting
reports. That makes it a useful system-status case, but the evidence supports specific
documented behaviors—not every visual or timing detail previously attributed to the product
([Stripe: Web Dashboard](https://docs.stripe.com/dashboard/basics)).

### Design Decisions

**1. Status is attached to the operational object**
- The Transactions area lists customer payments and their status
- Users can filter transactions and inspect related account resources
- The Dashboard home also surfaces unresolved disputes and identity-verification work

These capabilities are documented in
[Stripe's Dashboard guide](https://docs.stripe.com/dashboard/basics).

**2. Failure information supports a next action**
- When an issuer provides decline information, Stripe exposes it in the Dashboard and API
- Decline codes and failure messages provide diagnostic context
- Stripe's guidance distinguishes on-session recovery (ask for another payment method) from off-session recovery (notify the customer)

See [Stripe: Card declines](https://docs.stripe.com/declines/card).

**3. High-consequence actions expose scope before execution**
- The Dashboard refund flow starts from a specific payment
- A full refund is the default, while a partial refund requires an explicit amount
- A reason is required, with a note required for “Other”
- Stripe documents when refunds can be canceled and exposes refund state and reference details

See [Stripe: Refund and cancel payments](https://docs.stripe.com/refunds).

**4. Integration feedback preserves technical evidence**
- Workbench logs successful and failed API requests
- Logs include the original request, response, and related API resources
- Webhook delivery views distinguish Delivered, Pending, and Failed attempts and expose response details

Primary evidence:
[Stripe Dashboard: Monitor and test](https://docs.stripe.com/dashboard/basics#monitor-and-test-your-integration) and
[Stripe: View event deliveries](https://docs.stripe.com/webhooks#debug-webhook-integrations).

**5. Asynchronous changes are represented as events**
- Stripe can push event data to registered destinations when account activity occurs
- Events cover asynchronous outcomes such as bank confirmation, disputes, and recurring-payment success
- Stripe explicitly warns that duplicate delivery can occur and that event order is not guaranteed

See [Stripe: Receive events](https://docs.stripe.com/webhooks).

**6. Reporting turns status into a durable artifact**
- Dashboard reporting covers historical transactions, payments, and payouts
- Reports can be filtered, given custom columns, and exported
- Stripe's reporting documentation supports CSV download for accounting work

See [Stripe: Reporting](https://docs.stripe.com/stripe-reports).

Together, these patterns create a chain from business object → current status → diagnostic
detail → next action → event history or export. That chain is the transferable design lesson;
claims about toast placement, color, animation, WebSockets, or sub-second response are outside
the published evidence reviewed for this page.

## Transferable Design Analysis

The following are design inferences from the documented operational model, not Stripe-published
outcome findings.

### User Confidence & Trust
- **Visible object state** can reduce ambiguity about what the system recorded
- **Failure context** can make the next recovery step more specific
- **Event history** provides evidence when the current state alone is insufficient
- **Exports** let operators reconcile the interface with another record

### Error Prevention & Recovery
- **Scoped refund inputs** make amount and reason explicit
- **Status visibility** can discourage repeated actions made only to check whether the first worked
- **Decline detail** can route recovery to a new payment method or customer contact
- **Request and delivery logs** support self-service diagnosis before escalation

### Operational Efficiency
- **Object-level status** reduces the need to infer state from a separate log
- **Decline detail** supports a defined recovery path
- **Event-delivery history** gives developers evidence for integration failures
- **Exports** preserve operational data for reconciliation and analysis

### Business Implications
- **Traceability** from a payment or refund to its current state
- **Safer operations** through scoped actions and documented state transitions
- **Faster diagnosis** when API calls or event deliveries fail
- **Reconciliation support** through filterable and exportable reports

## Evidence Boundary

Stripe's public documentation establishes the Dashboard capabilities and state model above.
It does **not** publish the confidence, duplicate-action, support-ticket, task-time, or
satisfaction comparisons previously shown on this page. Those figures have been removed.

To evaluate feedback quality in a financial operations interface, measure:

| Measure | Method |
|---------|--------|
| State comprehension | Ask users to identify current state and next action from defined scenarios |
| Duplicate-action rate | Repeated mutations with the same intent, normalized by eligible actions |
| Recovery completion | Failed operations successfully resolved without support intervention |
| Diagnostic time | Time from an alert to the relevant request, event, or decline evidence |
| Reconciliation defects | Differences between product state and exported/accounting records |

## How to Apply This Pattern

### React Implementation Example

```tsx
import { useState } from 'react';

// Toast notification types
type ToastType = 'success' | 'error' | 'info' | 'warning';

interface Toast {
  id: string;
  type: ToastType;
  message: string;
  description?: string;
  duration?: number;
}

// Example toast notification component
export function ToastNotification({
  toast,
  onDismiss
}: {
  toast: Toast;
  onDismiss: () => void;
}) {
  const [isHovered, setIsHovered] = useState(false);

  // Auto-dismiss after duration (pause on hover)
  useState(() => {
    if (!isHovered && toast.duration) {
      const timer = setTimeout(onDismiss, toast.duration);
      return () => clearTimeout(timer);
    }
  });

  const icons = {
    success: '✓',
    error: '✗',
    info: 'ℹ',
    warning: '⚠'
  };

  return (
    <div
      className={`toast toast-${toast.type}`}
      role="status"
      aria-live="polite"
      onMouseEnter={() => setIsHovered(true)}
      onMouseLeave={() => setIsHovered(false)}
    >
      <div className="toast-icon" aria-hidden="true">
        {icons[toast.type]}
      </div>

      <div className="toast-content">
        <div className="toast-message">{toast.message}</div>
        {toast.description && (
          <div className="toast-description">{toast.description}</div>
        )}
      </div>

      <button
        onClick={onDismiss}
        className="toast-close"
        aria-label="Dismiss notification"
      >
        ✕
      </button>
    </div>
  );
}

// Toast container (manages multiple toasts)
export function ToastContainer({ toasts }: { toasts: Toast[] }) {
  return (
    <div className="toast-container" aria-live="polite" aria-atomic="false">
      {toasts.map(toast => (
        <ToastNotification key={toast.id} toast={toast} onDismiss={() => {}} />
      ))}
    </div>
  );
}

// Async action button with feedback states
export function AsyncActionButton({
  label,
  onAction,
  successMessage,
  errorMessage,
  variant = 'primary'
}: {
  label: string;
  onAction: () => Promise<void>;
  successMessage?: string;
  errorMessage?: string;
  variant?: 'primary' | 'danger';
}) {
  const [state, setState] = useState<'idle' | 'loading' | 'success' | 'error'>('idle');

  const handleClick = async () => {
    setState('loading');

    try {
      await onAction();
      setState('success');

      // Show success toast
      if (successMessage) {
        showToast({
          type: 'success',
          message: successMessage
        });
      }

      // Reset to idle after brief success state
      setTimeout(() => setState('idle'), 2000);
    } catch (error) {
      setState('error');

      // Show error toast
      showToast({
        type: 'error',
        message: errorMessage || 'An error occurred',
        description: error instanceof Error ? error.message : undefined
      });

      // Reset to idle after error shown
      setTimeout(() => setState('idle'), 3000);
    }
  };

  return (
    <button
      onClick={handleClick}
      disabled={state === 'loading'}
      className={`async-button ${variant} ${state}`}
      aria-busy={state === 'loading'}
    >
      {state === 'loading' && (
        <span className="button-spinner" aria-hidden="true">⏳</span>
      )}
      {state === 'success' && (
        <span className="button-icon" aria-hidden="true">✓</span>
      )}
      {state === 'error' && (
        <span className="button-icon" aria-hidden="true">✗</span>
      )}
      <span>{label}</span>
    </button>
  );
}

// Confirmation dialog for destructive actions
export function ConfirmationDialog({
  isOpen,
  onClose,
  onConfirm,
  title,
  message,
  confirmLabel = 'Confirm',
  isDangerous = false
}: {
  isOpen: boolean;
  onClose: () => void;
  onConfirm: () => Promise<void>;
  title: string;
  message: string;
  confirmLabel?: string;
  isDangerous?: boolean;
}) {
  const [isConfirming, setIsConfirming] = useState(false);

  const handleConfirm = async () => {
    setIsConfirming(true);
    try {
      await onConfirm();
      onClose();
    } catch (error) {
      // Error handling
      setIsConfirming(false);
    }
  };

  if (!isOpen) return null;

  return (
    <div className="dialog-backdrop" onClick={onClose}>
      <div
        className="confirmation-dialog"
        onClick={(e) => e.stopPropagation()}
        role="alertdialog"
        aria-labelledby="dialog-title"
        aria-describedby="dialog-message"
      >
        <h2 id="dialog-title">{title}</h2>
        <p id="dialog-message">{message}</p>

        <div className="dialog-actions">
          <button
            onClick={onClose}
            disabled={isConfirming}
            className="button-secondary"
          >
            Cancel
          </button>
          <button
            onClick={handleConfirm}
            disabled={isConfirming}
            className={isDangerous ? 'button-danger' : 'button-primary'}
          >
            {isConfirming ? 'Processing...' : confirmLabel}
          </button>
        </div>
      </div>
    </div>
  );
}

// Example status badge
export function StatusBadge({
  status,
  label
}: {
  status: 'success' | 'error' | 'pending' | 'warning';
  label: string;
}) {
  const icons = {
    success: '✓',
    error: '✗',
    pending: '⏳',
    warning: '⚠'
  };

  return (
    <span className={`status-badge status-${status}`} role="status">
      <span className="badge-icon" aria-hidden="true">
        {icons[status]}
      </span>
      <span className="badge-label">{label}</span>
    </span>
  );
}

// Skeleton loader for loading states
export function SkeletonLoader() {
  return (
    <div className="skeleton-loader" role="status" aria-label="Loading content">
      <div className="skeleton-line skeleton-line-full" />
      <div className="skeleton-line skeleton-line-75" />
      <div className="skeleton-line skeleton-line-50" />
    </div>
  );
}

// Global toast manager (simplified)
let toastCounter = 0;
const toastListeners: Array<(toast: Toast) => void> = [];

function showToast(toast: Omit<Toast, 'id'>) {
  const fullToast: Toast = {
    ...toast,
    id: `toast-${toastCounter++}`,
    duration: toast.duration || 5000
  };

  toastListeners.forEach(listener => listener(fullToast));
}
```

## Feedback Timing Guidelines

| Timing | Use Case | Pattern |
|--------|----------|---------|
| **\<0.1s** | Instant actions (button press, typing) | Visual state change only |
| **0.1-1s** | Fast operations (save draft, simple validation) | Loading indicator + success toast |
| **1-3s** | Medium operations (API calls, calculations) | Loading overlay + progress indicator |
| **3-10s** | Slow operations (file uploads, batch processing) | Progress bar with percentage + time estimate |
| **>10s** | Long operations (reports, exports) | Background task + email notification when done |

## Feedback Patterns by Action Type

| Action Type | Feedback Pattern | Example |
|-------------|-----------------|---------|
| **Create** | Success toast + show created item | "Payment created successfully" |
| **Update** | Optimistic UI + success toast | "Customer updated" (changes visible immediately) |
| **Delete** | Confirmation dialog + success toast + undo option | "Customer deleted" with 5s undo window |
| **Error** | Specific error message + recovery action | "Card declined. Ask customer to try another card." |
| **Background** | Progress notification + completion alert | "Export started. We'll email you when it's ready." |
